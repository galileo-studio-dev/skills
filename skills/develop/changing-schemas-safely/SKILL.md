# Changing Schemas Safely

## Overview

Schema changes are the one kind of change `git revert` cannot undo: the old column is gone, the new one is full, and the deploy is halfway through. They also run while the previous version of the application is still serving traffic. Most migration incidents come from forgetting one of those two facts.

**Core principle:** Every schema change is compatible with the code running *before* and *after* it, is reversible until the last step, and runs against shared data only with explicit approval.

## Before writing the migration

State, in the plan or in your reply:

- **Change:** the schema before and after.
- **Compatibility:** which application versions run against each state during rollout.
- **Data:** row counts of the affected tables, whether a backfill is needed, and what may lock for how long.
- **Rollback:** the reverse step for each forward step, and the point past which rollback needs a restore.
- **Approval:** who runs it, where, and when. Never run it against a shared database as part of "finishing the task".

This is the *Dependencias o migraciones* and *Rollback* section of the pull request template; fill it there.

## Expand, migrate, contract

Split a breaking change into steps that are each safe with both the old and the new code:

| Goal | Expand (deploy 1) | Migrate (data) | Contract (a later deploy) |
| --- | --- | --- | --- |
| Add a required column | Add it **nullable** or with a default; new code writes it | Backfill in batches | Add `NOT NULL`; drop a temporary default |
| Rename a column | Add the new column; code writes both, reads new then old | Backfill new from old | Stop writing old; drop old |
| Change a type | Add a new column of the new type; write both | Backfill with conversion | Switch reads; drop old |
| Drop a column | Stop reading it in code | — | Drop it, once no code references it |
| Add a constraint or foreign key | Add it `NOT VALID` (Postgres) | Fix violating rows | `VALIDATE CONSTRAINT` |
| Add an index on a large table | `CREATE INDEX CONCURRENTLY`, outside a transaction | — | — |
| Split or merge tables | Create the new table; write both | Backfill | Switch reads; drop old |

An additive, nullable change is usually one step. Everything else takes at least two deploys. "It's a small table" is how the large-table incident starts.

## Migration files

- One migration per logical change, with both directions (`upgrade`/`downgrade`, `up`/`down`) implemented and run locally against a copy of real-shaped data.
- Schema migrations and data backfills are separate. Backfills are batched, resumable, idempotent, and run outside the schema migration's transaction.
- No application models imported into migrations: models change, migrations must not. Use the tool's operations or raw SQL.
- Never edit a migration that has run anywhere other than your machine. Add a new one.
- Keep the model definition and the migration in the same change so they cannot drift.
- Read every line of a generated migration. Autogenerated diffs (Alembic, Prisma, Drizzle, the Supabase CLI) routinely drop and recreate things you did not intend.

## Locks and duration (Postgres)

- `ALTER TABLE ... ADD COLUMN` with a constant default is fast on Postgres 11 and later. A volatile default, or `NOT NULL` on existing rows, scans or rewrites the table.
- `CREATE INDEX` blocks writes; use `CONCURRENTLY`. Same for `DROP INDEX`.
- Adding a foreign key validates every row under a lock; use `NOT VALID`, then `VALIDATE`.
- Changing a column's type rewrites the table. Prefer the add-a-new-column path.
- Set `lock_timeout` (for example `SET lock_timeout = '5s'`) so a migration fails fast instead of queueing behind a long transaction and blocking the application.
- Long backfills: batch, pause between batches, watch replication lag.

## Destructive operations need explicit approval

`DROP TABLE`, `DROP COLUMN`, `TRUNCATE`, `DELETE` without a narrow `WHERE`, type changes that lose precision, and any `UPDATE` touching more rows than you can name. Before running one against anything but a local database:

1. Show the exact statement and the affected row count.
2. Confirm a backup or snapshot exists and how to restore it.
3. Wait for the person to say yes. A plan that mentions it is not approval.

## Example: rename `users.name` to `users.display_name` with Alembic

```python
# migrations/versions/0042_add_display_name.py — expand: additive and nullable
def upgrade():
    op.add_column("users", sa.Column("display_name", sa.Text(), nullable=True))

def downgrade():
    op.drop_column("users", "display_name")
```

Deploy: the application writes both columns and reads `display_name`, falling back to `name`.

```python
# scripts/backfill_display_name.py — data step: batched, idempotent, resumable,
# outside the migration transaction
with engine.connect().execution_options(isolation_level="AUTOCOMMIT") as conn:
    while True:
        n = conn.execute(sa.text("""
            UPDATE users SET display_name = name
            WHERE id IN (SELECT id FROM users WHERE display_name IS NULL LIMIT 5000)
        """)).rowcount
        if n == 0:
            break
        time.sleep(0.2)   # let replicas and other writers keep up
```

Deploy: the application reads and writes only `display_name`. In a later release:

```python
# migrations/versions/0043_drop_name.py — contract: only after no code references users.name
def upgrade():
    op.alter_column("users", "display_name", nullable=False)
    op.drop_column("users", "name")

def downgrade():
    op.add_column("users", sa.Column("name", sa.Text(), nullable=True))
    op.execute("UPDATE users SET name = display_name")
    op.alter_column("users", "display_name", nullable=True)
```

From 0043 onward, rolling back costs a table-wide `UPDATE`; say so in the pull request.

## Common mistakes

| Mistake | Consequence | Fix |
| --- | --- | --- |
| Rename in one migration | Old instances crash with `column does not exist` during rollout | Expand, migrate, contract |
| `NOT NULL` column with no default on a populated table | Migration fails, or the old code cannot insert | Nullable first, backfill, then constrain |
| Backfill inside the schema migration | One giant transaction, long lock, no way to resume | Separate, batched script |
| Importing models in migrations | Migration breaks when the model changes later | Tool operations or raw SQL |
| Applying a generated migration unread | Accidental drops, index churn | Read every generated line |
| Running migrations "to finish the task" | Shared data changed without approval | Ask; show the statement and the counts |
| No `downgrade` | Rollback means a restore from backup | Write it and run it locally |
